# Chameleon - спецификация v0.1 (черновик)

## 0. Главная идея

Сессия не привязана к соединению. Логическая сессия живёт отдельно, а данные
идут через одну или несколько «несущих» (carrier): TLS, WebSocket, HTTP через CDN,
QUIC. Каждая несущая - просто труба для зашифрованных record'ов.

```
┌──────────────────────────────────────────────────────┐
│  Приложение (TCP/UDP потоки пользователя)            │
├──────────────────────────────────────────────────────┤
│  СЕССИЯ: пакеты с номерами, фреймы, ACK, потоки      │  ← уникальна на всю сессию
├──────────────────────────────────────────────────────┤
│  ШЕЙПЕР: когда и какого размера отправлять (этап 3)  │
├──────────────────────────────────────────────────────┤
│  RECORD-СЛОЙ: AEAD + маскированная длина             │  ← свой ключ на каждую несущую
├───────────────┬───────────────┬──────────────────────┤
│  Несущая #1   │  Несущая #2   │  Несущая #N          │
│  (TLS)        │  (WebSocket)  │  (HTTP/CDN)          │
└───────────────┴───────────────┴──────────────────────┘
```

## 1. Ключи

Рукопожатие Noise IK (см. §6) выдаёт `session_secret` - 32 байта, одинаковые
у клиента и сервера, выведенные из финального chaining key рукопожатия.

Для каждой несущей с идентификатором `carrier_id` (uint32) выводятся 4 ключа
через HKDF-Expand-SHA256:

| Ключ         | info                                         |
|--------------|----------------------------------------------|
| c2s AEAD     | `"chameleon v1 c2s aead"` ‖ carrier_id (BE)  |
| c2s mask     | `"chameleon v1 c2s mask"` ‖ carrier_id (BE)  |
| s2c AEAD     | `"chameleon v1 s2c aead"` ‖ carrier_id (BE)  |
| s2c mask     | `"chameleon v1 s2c mask"` ‖ carrier_id (BE)  |

Благодаря `carrier_id` одна и та же сессия на разных несущих даёт
несвязанный между собой шифротекст.

## 2. Record-слой (потоковые несущие)

```
┌─────────────────┬──────────────────────────────┬──────────┐
│ masked_len (2)  │ ciphertext (N)               │ tag (16) │
└─────────────────┴──────────────────────────────┴──────────┘
```

- Шифр: ChaCha20-Poly1305. Где ОС поддерживает нативную реализацию (Windows 11,
  Linux/OpenSSL) - берётся она; иначе (например Windows 10) - переносимая
  реализация на чистом C# по RFC 8439. Поведение одинаковое, зависимостей нет.
- `nonce = 0x00000000 ‖ counter (uint64 BE)`, счётчик свой у каждого направления каждой несущей.
- `len = N + 16`, допустимо от 16 до 16384+16.
- `masked_len = len XOR AES-256-ECB(mask_key, 0^8 ‖ counter)[0..2]`.

Зачем маскировать длину: в потоке нет ни одного открытого поля. Для наблюдателя
это равномерно случайные байты. Неверная длина ломает проверку тега, поэтому
отдельная аутентификация длины не нужна.

Любая ошибка (плохая длина, неверный тег) - несущая закрывается без ответа.
В будущем вместо закрытия будет передача соединения фейковому веб-серверу.

## 3. Сессионный пакет (открытый текст внутри record'а)

```
packet_number (varint) ‖ frame* 
```

`packet_number` уникален в пределах направления **всей сессии**, а не несущей.
Поэтому пакет, потерянный на несущей #1, можно переотправить через несущую #2,
а ACK может прийти по любой из них.

Пока несущая одна и надёжная (TCP, дальше TLS-over-TCP), доставку и порядок
гарантирует транспорт под нами, поэтому ретрансмиты и пересборка по offset НЕ
задействованы - номер пакета и offset проставляются, но нужны только когда
появится мультипуть (этап 4). Это осознанное упрощение, а не недоделка.

Varint - как в QUIC: 2 старших бита первого байта задают длину 1/2/4/8 байт,
максимум 2^62−1.

## 4. Фреймы

| Тип  | Имя          | Поля                                                                 |
|------|--------------|----------------------------------------------------------------------|
| 0x00 | PADDING      | - (каждый нулевой байт - отдельный фрейм)                            |
| 0x01 | PING         | -                                                                    |
| 0x02 | ACK          | largest, delay_ms, range_count, first_range, (gap, length)×count     |
| 0x03 | STREAM_OPEN  | stream_id, kind (u8), addr_type (u8), addr, port (u16 BE)            |
| 0x04 | STREAM       | stream_id, offset, length, data                                      |
| 0x05 | STREAM_FIN   | stream_id, final_offset                                              |
| 0x06 | STREAM_RESET | stream_id, error_code                                                |
| 0x07 | MAX_DATA     | stream_id (0 = вся сессия), max_offset                               |
| 0x08 | CLOSE        | error_code, reason_len, reason (UTF-8)                               |

- `kind`: 0 = TCP, 1 = UDP.
- `addr_type`: 1 = IPv4 (4 байта), 2 = IPv6 (16 байт), 3 = домен (u8 длина + байты).
- Все числа, кроме явно указанных, - varint.
- STREAM содержит `offset`, потому что куски одного потока могут прийти по разным
  несущим в разном порядке, и получатель собирает их по смещению.
- PADDING в конце пакета - основной инструмент шейпера: размер record'а
  выбирает модель поведения, а не приложение.

## 6. Рукопожатие (Noise IK)

Строка протокола: `Noise_IK_25519_ChaChaPoly_SHA256`, prologue `"chameleon v1"`.
Клиент заранее знает публичный статический ключ сервера (как в VLESS/Reality).

```
pre-message: сервер s          (обе стороны подмешивают публичный ключ сервера в h)
msg1  client -> server: e, es, s, ss      (96 байт при пустом payload)
msg2  server -> client: e, ee, se         (48 байт при пустом payload)
```

Свойства:
- клиент аутентифицирует сервер по известному ключу: зонд без ключа не пройдёт;
- статический ключ клиента (`s`) уходит уже зашифрованным внутри AEAD;
- forward secrecy за счёт эфемерных ключей `e` с обеих сторон;
- payload в msg1 пустой: сообщение может быть переиграно (replay), поэтому данные
  идут только после msg2, по установленным ключам.

`session_secret = HMAC-SHA256(chaining_key, "chameleon v1 session secret")`.

Присоединение доп. несущих (без нового Noise): клиент шлёт join = session_id(16) ‖
carrier_id(4) ‖ nonce(16) ‖ HMAC(join_key, …)(16), где session_id/join_key
выведены из session_secret. Сервер находит сессию по session_id, проверяет tag,
отвечает HMAC(join_key,"ack"‖nonce) и цепляет несущую к сессии. Диспетчеризация
на сервере - по длине первого сообщения: 96 = Noise (новая сессия), 52 = join,
иначе - декой-прокси.

Сообщения рукопожатия идут с 2-байтным префиксом длины и своим ключом на
несущую. Поверх TLS-несущей (§8) всё это едет уже внутри TLS.

## 7.5. Шейпер трафика

Все исходящие record'ы проходят через шейпер (`TrafficShaper`), который скрывает
два поведенческих признака туннеля:

- **Квантование размеров** - пакет дополняется PADDING'ом (фреймы 0x00, приёмник
  их игнорирует) до ближайшего размера из короткой «лесенки», например
  {128, 512, 1536, 4096, 16384}. На проводе видно лишь несколько фиксированных
  длин вместо настоящих размеров нагрузки.
- **Прикрытие в простое** - пока данных нет, уходят пустые (только PADDING)
  пакеты. Тайминги задаёт не постоянный период (сам по себе «метроном» -
  отпечаток), а конечный автомат модели: паузы и размеры берутся из
  распределений текущего режима, режимы переключаются вероятностно.

Модель (`TrafficModel`) = лесенка размеров + набор режимов (`TrafficRegime`) с
временем пребывания, распределением пауз/размеров и весами переходов. Есть
пресеты `WebBrowsing` (всплеск/затишье) и `Streaming` (крупные пакеты, плотнее).
Модель можно сменить на лету (`TrafficShaper.SwitchModel`) - приёмная сторона о
модели ничего не знает, поэтому смена соединение не рвёт.

Модели загружаются/сохраняются в JSON (`TrafficModelIo`, на Utf8JsonWriter/
JsonDocument - без рефлексии, AOT-совместимо) и строятся из сэмплов реального
трафика (`TrafficModelIo.FromSamples`: размеры -> лесенка по перцентилям + веса из
гистограммы; паузы -> диапазоны режимов по медиане). Так модель можно «обучить»
на записи трафика, положить в файл и подставить.

## 8. Несущие

Несущая - это транспорт, внутри которого едут record'ы. Всё работает поверх
абстрактного потока (`Stream`), поэтому несущие взаимозаменяемы.

- **Голый TCP** - только для локальных тестов. Снаружи выглядит как поток
  случайных байтов, ТСПУ отсеет на дешёвом слое. Не для реальной сети.
ВАЖНО про надёжность несущей: record-слой использует неявный счётчик на каждый
record (§2) для nonce и маски длины. Потеря отдельного record рассинхронизирует
счётчик - поэтому КАЖДАЯ несущая обязана быть надёжной и упорядоченной (TCP/TLS).
Потери/переупорядочивание возможны лишь на уровне сессии между несущими (смерть
несущей, раскладка пакетов по разным несущим) - отсюда надёжная доставка (4-2) и
мультипуть (4-3) связаны и делаются вместе.

- **TLS** - настоящее TLS 1.3-соединение, внутри которого идёт Chameleon.
  Снаружи неотличимо от обычного HTTPS. Рукопожатие Noise и все record'ы едут
  уже внутри TLS. На неудачное внутреннее рукопожатие (мусор/зонд) сервер
  работает как обратный прокси к сайту-декою: активный зонд без ключа Noise
  получает живой контент настоящего сайта-прикрытия (как в Reality), а не
  заглушку, и не видит реальную цель. Байты зонда буферизуются и переигрываются
  декою, чтобы тот получил неусечённый запрос.

### Известное ограничение TLS-несущей: отпечаток ClientHello

ClientHello формирует `System.Net.Security.SslStream` (SChannel/OpenSSL). Это
валидный TLS 1.3, но по JA3/JA4 он НЕ совпадает с браузером: в .NET нет
управления порядком расширений и значениями GREASE. Для ТСПУ, который умеет
фильтровать по несовпадению отпечатка, это слабое место.

Решение - TLS-стек BouncyCastle, где мы задаём ClientHello сами (проект
`Chameleon.Tls`, `BcTlsCarrier.Client`). BC-клиент совместим с
обычным SslStream-сервером, поэтому серверную сторону менять не нужно. Отпечаток
можно измерять утилитами `Ja3`/`Ja4`. По JA4 (сортирует расширения, игнорирует
GREASE - ровно то, чем BC не управляет) достигнут профиль Chrome:
`t13d1516h2_8daaf6152771_…` - ja4_a и хеш шифров ja4_b совпадают с Chrome. Третья
часть ja4_c подгоняется под целевую сборку Chrome (подэтап 2б-4). Точный JA3 под
Chrome на стоковом BC недостижим (порядок расширений и GREASE) - для этого нужен
патч BC или внешний uTLS-слой.
